# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A backend service (FastAPI + PostgreSQL + Celery/Redis) for an e-commerce company with multiple warehouses: manage products/inventory, reserve stock safely under concurrent demand, process orders asynchronously with simulated payments, and keep a full audit trail. Built as a single modular monolith plus background workers, not microservices, by explicit design choice.

## Commands

### Run the app (Docker — preferred)

```bash
cp .env.example .env
docker compose up --build
```

Brings up Postgres, Redis, the API (`localhost:8000`), a Celery worker (order processing), Celery Beat (reservation-expiry scheduler), and the outbox relay process. On first boot the `api` service runs `alembic upgrade head` then `python -m src.bootstrap` (creates a default ADMIN user from `DEFAULT_ADMIN_EMAIL`/`DEFAULT_ADMIN_PASSWORD`) before starting uvicorn. Docs at `/docs`.

### Run the app (local Python, no Docker)

```bash
python -m venv .venv && source .venv/bin/activate   # .venv\Scripts\activate on Windows
pip install -r requirements.txt
cp .env.example .env   # point DATABASE_URL/REDIS_URL at your local Postgres/Redis
alembic upgrade head
python -m src.bootstrap
uvicorn src.main:app --reload                                  # terminal 1: API
celery -A src.workers.celery_app worker --loglevel=info        # terminal 2
celery -A src.workers.celery_app beat --loglevel=info          # terminal 3
python -m src.workers.outbox_relay                             # terminal 4
```

### Tests

Tests run against a **real PostgreSQL database**, not SQLite/mocks — the whole point of this project is database-level concurrency/locking behavior, which SQLite cannot faithfully reproduce.

```bash
docker compose up -d postgres     # only Postgres is needed; tests don't need Redis/Celery
pytest                             # unit + integration + concurrency
pytest --cov=src
pytest tests/concurrency -v        # just the required 100-concurrent-request tests
pytest tests/unit/test_inventory_service.py                                    # one file
pytest tests/unit/test_inventory_service.py::test_reserve_succeeds_when_enough_stock -v  # one test
```

Tests connect to `TEST_DATABASE_URL` (default `postgresql+psycopg2://postgres:postgres@localhost:5432/inventory_db_test`, auto-created by `scripts/init-test-db.sql` on first Postgres container init). `tests/conftest.py` overrides `DATABASE_URL` with `TEST_DATABASE_URL` *before* anything under `src/` is imported — every module reaches the DB through `src.database.SessionLocal`, bound once at import time. Schema is created directly from the SQLAlchemy models (`Base.metadata.create_all`), not via Alembic, so tests don't depend on migration history; every table is truncated after each test. Celery runs in **eager mode** (`task_always_eager=True`) during tests — no broker needed, `.delay()` executes synchronously in-process.

There is no linter/formatter configured in this repo.

### Migrations

Migrations are hand-written, not autogenerated (`migrations/versions/000N_*.py`, sequential integer revisions). `alembic upgrade head` applies them; `downgrade()` is always implemented too, including explicit `DROP TYPE` for Postgres enums (Postgres doesn't drop enum types automatically when the column is dropped).

## Architecture

### Layering (strict, one-directional)

```
api/            HTTP only: request parsing, JWT auth, RBAC, status codes — calls straight into services/
services/       business rules + transaction boundaries (db.commit()/db.rollback() live here)
repositories/   one function per query/mutation, no business rules, no AppError, no HTTP knowledge
models/         SQLAlchemy ORM tables
schemas/        Pydantic request/response contracts
workers/        Celery tasks, beat schedule, outbox relay — reuse the same services/ functions the API uses
core/           ID generation, JWT/password hashing, exception hierarchy
middleware/     request-ID correlation, global error-envelope handler
```

`api/` never talks to `repositories/` directly. Repository functions return a bool/rowcount rather than raising on a failed conditional write (e.g. "0 rows updated"); the calling service decides what that means in context (insufficient stock vs. already-released vs. ...) and raises a typed `AppError` if appropriate.

### Transaction-boundary convention (important before adding any mutation)

Most `services/` functions that mutate inventory/reservations (`reserve`, `release_reservation`, `consume_reservation`) deliberately do **not** call `db.commit()`. They're building blocks composed by a caller that owns a larger unit of work (e.g. `order_service.create_order` reserves every line item, then creates the order/reservations/outbox row, then commits once — so a failure partway rolls back everything). Only the top-level caller commits: `order_service.create_order`, `order_service.cancel_order`, `workers/order_processor.process_order`, and standalone single-step endpoints like `inventory_service.create_adjustment` own their own transaction and commit directly. When adding a new mutation, match whichever pattern the call site needs instead of committing reflexively inside a low-level helper.

### Concurrency: atomic conditional UPDATE, not SELECT ... FOR UPDATE

The core correctness mechanism (see `docs/decisions/0001-concurrency-strategy.md` and `src/repositories/inventory_repository.py`'s module docstring). Every inventory mutation is a single guarded UPDATE, e.g.:

```sql
UPDATE inventory SET available_quantity = available_quantity - :qty, reserved_quantity = reserved_quantity + :qty
WHERE product_id = :pid AND warehouse_id = :wid AND available_quantity >= :qty
```

Postgres serializes concurrent UPDATEs to the same row; the loser's WHERE clause is re-evaluated against the winner's committed value and matches 0 rows, so the caller correctly reports failure with zero risk of a lost-update race — no `SERIALIZABLE` isolation or manual locking needed. This same compare-and-swap idiom is reused everywhere a "detect a state flip without double-processing under concurrency" problem shows up (e.g. `try_flip_low_stock`/`try_reset_low_stock` for low-stock alerts): guard the WHERE clause on the *current* state so only one of any number of racing transactions can ever see its UPDATE match. `CHECK` constraints on the table (`available_quantity >= 0`, etc.) are the final backstop.

### Transactional outbox

Async side effects (enqueueing a Celery task after a DB commit) are never fired directly — the natural `db.commit(); task.delay(...)` pattern loses the message if a crash lands between the two lines. Instead, an `outbox_events` row is written in the **same transaction** as the business write (see `order_service.create_order` writing `ORDER_RESERVED`), and a separate long-running process (`src/workers/outbox_relay.py`) polls for `PENDING` rows, calls the mapped Celery task, and only marks the row `PUBLISHED` after `.delay()` returns. This trades occasional duplicate delivery (on a crash between "enqueue" and "mark published") for the guarantee that a committed change can never fail to be enqueued — which is why consumers of these events (`order_processor.process_order`, `low_stock_notifier.notify_low_stock_task`) must tolerate being invoked more than once for the same event. New event types are wired into `outbox_relay.py`'s `_HANDLERS` dispatch dict. Full rationale: `docs/decisions/0003-outbox-pattern.md`.

### Idempotency (client-supplied `Idempotency-Key`)

A dedicated `idempotency_keys` table plus a claim/lock protocol: the first request with a key `INSERT`s a row (the primary-key constraint makes exactly one request "win" a race), does the work, and stores the response; a concurrent/later request with the same key locks the existing row and replays the cached response instead of double-creating. Reusing a key with a different request body is rejected. Details: `docs/decisions/0002-idempotency.md`.

### Error handling

Business-rule failures raise a typed subclass of `AppError` (`src/core/exceptions.py`) from `services/`/`workers/` — never ad-hoc HTTP responses from inside that code, since workers have no HTTP context at all. A single global handler (`src/middleware/error_handler.py`) renders any `AppError` (and normalizes Pydantic `RequestValidationError`) into the consistent envelope `{"error": {"code", "message", "details"}}`.

### Auth & RBAC

JWT bearer tokens (`POST /api/v1/auth/login`). Two roles, `ADMIN` and `CLIENT`; endpoints declare required roles via the `require_roles(...)` FastAPI dependency (`src/api/deps.py`). CLIENT users only ever see/act on their own orders; ADMIN sees/acts on everything. Route registration order matters when a fixed path segment could otherwise be captured by a sibling `{path_param}` route on the same router (e.g. `GET /inventory/low-stock` must be registered before `GET /inventory/{product_id}`).

### Order lifecycle

```
PENDING -> RESERVED -> PROCESSING -> COMPLETED   (payment_token: "success")
PENDING -> RESERVED -> PROCESSING -> FAILED       (payment_token: "fail")
PENDING -> RESERVED -(retry x2, backoff 5s/30s)-> FAILED   (payment_token: "fail_retryable")
RESERVED -> CANCELLED           (client cancels; PENDING also cancellable)
RESERVED -> EXPIRED             (reservation timeout elapses, default 15 min)
```

Reservation is synchronous (inside the order-creation request); payment simulation and order finalization happen asynchronously via the Celery worker after the outbox relay dispatches it. `COMPLETED` permanently consumes the reservation; `FAILED`/`CANCELLED`/`EXPIRED` release it back to available. Retry attempt count lives in the DB (`orders.processing_attempts`), not just Celery's in-memory counter, so it survives a worker restart.

### Why synchronous SQLAlchemy, not `async def`

Every DB-touching function uses a plain `Session`, not `AsyncSession` — the interesting engineering problem here is transaction/locking correctness, not raw I/O concurrency, and sync SQLAlchemy makes transaction boundaries trivial to read top-to-bottom. FastAPI still serves concurrent requests (sync `def` handlers run in a thread pool), and Celery itself is synchronous, so the API and workers share one mental model.

### Low-stock alerts add-on

A secondary feature layered on the above without touching the order flow: `Inventory.low_stock_threshold`/`is_low_stock` track per-(product, warehouse) alert state; `inventory_service._check_low_stock_transition` runs inside every mutation that changes `available_quantity` (reserve/release/adjust — not consume, which only moves `reserved_quantity`) and uses the same atomic-UPDATE compare-and-swap idiom to flip state and fire at most one alert per crossing under concurrency. Full writeup: `docs/decisions/0005-low-stock-alerts.md`.
